# Homegroups Performance & Scalability Audit — 2026-07-07

**Scope:** `homegroups/mobile/src/` (277 files, ~105K lines) and `homegroups/functions/src/` (225 files, ~53K lines). Web (`homegroups/web/`) out of scope. Builds on the Phase 1 review context (`serializableCheck` disabled, `onMemberCreate` fan-out, god screens, missing models, `generatePDF` risk).

**Method:** Four parallel deep-dive investigations — mobile store/models, mobile screens/navigation, functions callable, functions triggers/pubsub/indexes — each reading actual source and citing line numbers. Findings below are merged, deduplicated, and ranked by severity within each area.

---

## Executive Summary

The two most consequential scaling risks in the codebase are:

1. **`onMemberCreate`'s unchunked per-member fan-out** (Cloud Functions) grows **O(N²)** cumulatively as a group grows, and none of the 17 Firestore triggers or 14 pubsub jobs override the 256MB/60s v1 defaults — meaning this trigger, `scheduledGroupBackups`, and `scheduledDailyReflection` are all one bulk-import/growth-milestone away from timing out or OOM-ing with no alerting in place.
2. **Two silently-failing cron jobs from index mismatches**: `scheduledPositionReminders` (missing collection-group index entirely) and `scheduledMeetingReminders` (composite index fields in the wrong order) are very likely throwing `FAILED_PRECONDITION` on every run today, caught by a try/catch and logged as errors rather than surfacing — this needs a same-week production-log check, not just a code fix.

On mobile, the known "`useSelector`-inside-`renderItem`" bug class from `GroupLiteratureBookmarksScreen` has **not recurred** anywhere else — that's a clean bill of health. But a **new, more expensive version of the same failure mode** was found: an unthrottled Firestore _write_ on every keystroke in `GroupChatScreen`'s typing indicator, fanning out to a full unbounded collection read in `GroupOverviewScreen` because React Navigation doesn't unmount it underneath the chat screen. There's also a confirmed listener leak in `TreasurerHandoffScreen` (no cleanup captured) and two client-side N+1 patterns (unbounded `Promise.all` fan-out in `BusinessMeetingModel`, fully sequential per-member fetch in `DirectMessageModel` and `TreasurerHandoffScreen`).

The `serializableCheck: false` and god-screen concerns from Phase 1 are both confirmed as real but currently **moderate**, not critical — they're architecture debt that will compound as screens/state grow, rather than active production incidents today.
