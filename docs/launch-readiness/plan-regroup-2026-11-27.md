## 1. Verdict

No. Regroup can't take a live payment today. The code is largely ready: every engineering half of the 2026-11-21
blockers is on `main`. Production hasn't moved since then:

- **Functions** were last deployed 2026-11-11 and still authenticate to the Homegroups App Stripe account
  (`STRIPE_SECRET_KEY@3`), with test-mode annual price IDs and no `CONNECT_BASE_URL`.
- **Rules** are from 2026-11-11, and four indexes on `main` aren't deployed.
- **Hosting** dates from 2026-10-07: `/invite`, `/checkout-return` and `/connect/*` all show the 404 page.

**The binding constraint is that production deploy**, which waits only on the owner lifting the freeze. Live
Stripe still holds 7 active legacy subscriptions and production 2,919 user records; the owner confirmed on
2026-11-27 that all of them are outdated, inactive or test accounts, so the "no live users" premise stands, but one
of those subscriptions still charges a card every month (M7). After the deploy come:

- the Dashboard checks (above all, which account owns the web publishable key);
- a final privacy policy;
- three small store-upload fixes;
- new store builds through review;
- a live smoke test of both money paths before sales open.

Expect one to two weeks, dominated by legal review and App Review rather than code.

## 4. Risks

- **Low: the redeploy reaches old accounts.** Seven live subscriptions and 2,919 user records exist (MS-15). The owner confirmed (2026-11-27) that all are outdated, inactive or test accounts. The one still billing is M7.
- **High: the web publishable key belongs to another account.** It's valid, but its owner is unknown (MS-18). If
  it's wrong, every web checkout fails at card confirmation, after the deploy looks healthy. B2(a) or, at the
  latest, B6 catches it.
- **High: App Review rejects the build.** Missing purpose strings (B5a), the external-purchase call to action for
  plans, or a lapsed operator with no delete (S3) each cost a review cycle.
- **High → closed in code: a co-owner or a stale save redirects rent** (M1, #331). Live only after B1's rules deploy.
- **Medium: invitations that never arrive look sent** (M3): fixed in code (#332, #334), live after B1 and the B5 build. With no DMARC record they may still land in spam (B2c).
- **Closed: concurrent subscription writes** (M5, #327, merged 2026-11-28).
- **Medium: no alerting** (M4): the first failed rent run or webhook is found by a customer.
- **Medium: the data has PITR only** (7 days), no backups, and delete protection off (S7).
- **Low: Android invitees land on the web page** until the Play SHA-256 is in `app-links.json` (B5).
