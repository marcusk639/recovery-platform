# Regroup coverage matrix

**The launch acceptance checklist** (regroup launch design §4.3, §9). Every user action × role × platform × fixture the relaunch must prove, with what proves it and its last result.

`scripts/coverage-matrix-check.js` validates this file and gates the phases (launch roadmap, `docs/superpowers/plans/2026-11-06-regroup-launch-roadmap.md`):

- P6: `node scripts/coverage-matrix-check.js --release --exclude-kinds device`
- P7: `node scripts/coverage-matrix-check.js --release --kinds device --id-prefix DEVS-`
- before launch step 10.5: `node scripts/coverage-matrix-check.js --release`

## Columns

| Column     | Values                                                                                                                    |
| ---------- | ------------------------------------------------------------------------------------------------------------------------- |
| ID         | `AREA-NNN`, unique. Device rows: `DEVS-NNN` (staging pass, P7), `DEVP-NNN` (production pass, P9).                         |
| Role       | `signed-out`, `operator`, `manager`, `resident`, `oxford`, `any`                                                          |
| Platform   | `ios`, `android`, `both` (must pass on both), `web`                                                                       |
| Fixture    | `clean`, `legacy`, `both` (must pass on both), `n/a`                                                                      |
| Kind       | `maestro`, `playwright`, `staging`, `device`, `unit`                                                                      |
| Covered by | repo-relative path of the flow, test or script that proves the row; a checklist item for `device` rows; `—` while missing |
| Guard      | `money`, `data`, `none`. Money and data rows can never be deferred.                                                       |
| Status     | `pass`, `fail`, `missing`, `deferred`                                                                                     |
| Deferred   | `<checklist\|post-launch>: <reason> (YYYY-MM-DD)`, or `—`                                                                 |

## Rules

- A row is `pass` only when its covering test asserts the outcome (the resulting screen state, and the Firestore document where it matters), not just a tap-through. A flow with an optional key step leaves its row `fail` (spec §2, §3.5).
- **Deferring a row (owner decision, spec §4.3):** the owner may defer a specific row to the manual device checklist or, if it touches neither money nor data, to a post-launch fix list, with the reason and date written here. Money-path rows (checkout, charges, grace and lapse, the sales-open switch, the paywall states) and data-access rows (payment history, documents, the backfill outcomes) are never deferrable: they pass or there is no release.
- Rows are added when the suite turns up something this list missed. Rows are never removed to make the count work.
- Created 2026-11-06 (P1). The six parity flows were run on iOS and Android on RN 0.88 in P2 (decision record §7.2). Rows whose key step is optional or never ran (signup's landing, the dispute modal, the week-summary card) are `fail` until P6 strengthens them. The `linking` config is unused today (spec §3.3). Its routes get one row per route group, which P5 splits into per-route rows when it wires the corrected config.
