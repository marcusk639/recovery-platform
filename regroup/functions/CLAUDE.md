# Cloud Functions

This directory contains the Firebase Cloud Functions backend for Regroup. Loaded by Claude Code automatically when working inside `functions/`. See `../CLAUDE.md` for project-wide rules (including Stripe and PII policy).

## Commands

```bash
npm run build                   # TypeScript compile
npm run lint                    # ESLint + typescript-eslint, type-aware (eslint.config.mjs; replaced tslint, #113). Errors fail it; warnings don't
npm test                        # Jest unit tests (run in band)
npm run test:watch              # Jest watch mode
npm run test:coverage           # Jest with coverage
npm run serve                   # Build + legacy `firebase serve --only functions`
npm run preflight:billing       # Billing preflight (also the firebase.json predeploy hook); refuses a deploy only when neither functions/.env nor functions/.env.<project> exists
npm run env:write -- --project phoenix-cleanhouse    # Writes the gitignored functions/.env.phoenix-cleanhouse from ../scripts/stripe-prices.env
npm run stripe:verify-live -- --project phoenix-cleanhouse   # Read-only: the latest STRIPE_SECRET_KEY is Regroup's account and every tier price is live at the right amount
npm run stripe:listen           # Forward Stripe events to local stripeEvents + handleStripeConnectWebhook
npm run deploy                  # Only `firebase deploy --only functions`: NO build, so it ships lib/ as it is (stale or missing). Don't use it to deploy
npm run deploy:batched -- --project <id>   # Batched fallback for deploy quotas only; builds first, refuses without --project
```

**Deploy** from `regroup/`, building first: `npm --prefix functions ci && npm --prefix functions run env:write -- --project phoenix-cleanhouse && npm --prefix functions run stripe:verify-live -- --project phoenix-cleanhouse && npm --prefix functions run build && firebase deploy --only functions`. The deploy config lives only in the gitignored `functions/.env.<project>`, so a clean worktree has none until `env:write` writes it, and the preflight refuses the deploy without it. `regroup/firebase.json`'s `functions.ignore` keeps `*.local`, `service-key.json`, `.claude/` session files and `coverage/` out of the upload. `package.json` `main` is `lib/index.js`, and the `functions.predeploy` hook in `regroup/firebase.json` runs only `scripts/preflight-billing.js`, never the TypeScript build.

**One-time IAM, per project, before documents can open:** `getDocumentLink` signs a v4 URL with no private key, through the IAM Credentials `signBlob` API, so the functions' runtime account (`<project number>-compute@developer.gserviceaccount.com`) needs `roles/iam.serviceAccountTokenCreator` on itself. Editor doesn't include it. Without it every call fails as `internal` and the app shows "Couldn't open the document". Grant it with `gcloud iam service-accounts add-iam-policy-binding <number>-compute@developer.gserviceaccount.com --member=serviceAccount:<number>-compute@developer.gserviceaccount.com --role=roles/iam.serviceAccountTokenCreator --project <project>`, and keep `iamcredentials.googleapis.com` enabled. Check with `gcloud iam service-accounts get-iam-policy <number>-compute@developer.gserviceaccount.com --project <project>`. On 2026-11-14 `regroup-e2e` had the API enabled but no grant.

**Migration scripts** (each runs `npm run build` first; dry-run is the default, `--apply` writes for the cents migrations):

Combined #141/#145 deploy order (regroup/CLAUDE.md): #145 step 0 and backfills → functions (build first) → the MERGED ruleset immediately after → this, at least 10 minutes later, with `-- --verify-stamps` (cutoff = run start; re-derives pre-rules stamps; flags differing ones on disputed activities, exit 3) → #145's remaining steps → app

Jest config is the `jest` key in `package.json` (no `jest.config.js`). Firestore rules tests live in `../mobile/firebase/__tests__/`, not here.

> **Node ≥ 23 gotcha:** the firebase-admin → jsonwebtoken → jwa chain loads `buffer-equal-constant-time`, which crashes on Node ≥ 23 (SlowBuffer removed; no upstream fix exists). Jest maps it to `test-shims/buffer-equal-constant-time.js` so `npm test` works on any Node; deployed runtime is Node 22 (`engines`). Non-Jest local scripts that load firebase-admin auth still need Node ≤ 22.

## Domain Rules

### Rent charges

Oxford houses are never charged this way: their dues are the members' equal expense share (`ees-records`), and `rentSettingsOf` and the rules keep price charging off there. When a house's charging turned on lives in server-only `rentHouseStates/{houseId}`, never on the house doc. Its writer is `onHouseRentSettingsWrite` (`triggers/firestore/houseRentSettings.ts`, retried): on a change to `rentFrequency`, `monthlyRent`, `weeklyRent`, `timezone` or `houseType` it stamps the house-local start day when charging turns on and clears it when charging turns off, deciding from the current house doc so redelivered or out-of-order events converge. `src/rent/chargeResident.ts` is the only writer that adds rent to `rentOwed` (hourly `rentCharges` job, `onGuestWrite`, catch-up). Records live in server-only `rentAccounts` / `rentCharges`. Stop switch: set `config/rentCharges.paused = true` (stops every charge without a deploy); `npm run rent:reverse:dry-run -- --house=ID` / `rent:reverse:apply` reverses by record and refuses unless paused or the house's charging is off. A reversal frees those days to be charged again, so un-pausing (or turning the house's charging back on) re-charges them unless the cause is fixed first.

Sales-open switch: `config/sales.open` (`util/salesSwitch.ts`) decides whether new tier subscriptions can start. Missing, non-boolean or unreadable means closed. `createOperatorSubscription` and the canceled branch of `reactivateOperatorSubscription` read it on every call and refuse while it's closed; `getTierCatalog` reports it as `salesOpen` (cached 60s) with `trialDays`. Closed in production from the backend deploy until launch step 10.5; open on staging and the emulators (the payment suite's `globalSetup` opens it). Set it with `npm run switch:set`.

Minimum app version: `config/app.minVersion.{ios,android}` (`x.y` or `x.y.z`), served by the public `getAppConfig`. An app build older than its platform's value shows the update screen; anything missing, malformed or unreadable lets everyone in. Change it without a deploy: `npm run switch:set -- --switch=minVersion --platform=ios --value=1.54` (dry run; add `--apply` to write), and `--value=none` removes it. Callers see a change within 60 s (per-instance cache; the emulator doesn't cache). Set it only once that version is downloadable in that store (launch step 10.6), or nobody on that platform can get in; lowering it or `none` lets them straight back in.

### Stripe amounts

All Stripe amounts are in **US cents** (integers). `50000` = $500.00. Convert only at the UI boundary — never inside function logic.

### Bundle discounts (dormant)

`api/stripe.ts` (`getBundleCoupon`, `applyBundleDiscountToSubscription`, `removeBundleDiscount`) is legacy per-house code and never fires: the `applyBundleDiscount` callable early-returns for any sub carrying a `tier`, and every surviving sub is a tier sub. Do not wire it to tiers without a pricing decision (tier level already prices multi-property; pricing gate P-6). Coupons exist in Stripe test mode only.

### Tier capabilities (value ladder, P-7/P-8)

Each tier in `SUBSCRIPTION_TIERS` carries a `features` map
(`automatedRentCollection`, `multiProperty`, `complianceExport`, `analytics`,
`whiteLabel`) expressing the value ladder. Gate features at their real call site
with `tierAllows(houseType, tier, featureKey)` (`util/tierPricing.ts`) — **compose
with the `maxResidents`/`maxProperties` caps, don't replace them**. Currently
enforced: `multiProperty` in `updateSubscriptionHouses` (capability-specific error
before the numeric cap); `complianceExport` in the `complianceExport` callable
(`callable/compliance.ts`, RG-SPEC-09 — returns `upgrade_required` when the tier
lacks it, else a real court/drug-court export of drug tests + meeting attendance,
issue #31: `format: "csv"` (default; returns `csv`) or `"pdf"` (returns `pdfBase64`)); and `analytics` in the `rentRoiMetrics` callable
(`callable/analytics.ts`, RG-TRACK — returns `upgrade_required` else rent-collection
ROI metrics, issue #32). The remaining flags (`automatedRentCollection`,
`whiteLabel`) are defined value-ladder labels; do not gate a capability that has no
real feature behind it.

**Read-only money/PHI note:** both `complianceExport` and `rentRoiMetrics` are
read-only and log only ids + aggregate counts (never names, test results, or
amounts per resident). `payments` docs store `amount` in integer **cents**
(`handlePaymentIntentSucceeded` writes `paymentIntent.amount` as is; its
`amountDollars` is only for notification copy), the same unit as
`guests.rentOwed`; `rentRoiMetrics` sums it without converting. `rentRoiMetrics` returns `collectedGrossCents`, `refundedCents`,
`collectedNetCents` (gross − refunds), `outstandingCents`, `overdueResidentCount`,
and `onTimeRatePct`/`duePaymentCount`. Refunds are recorded by the
`charge.refunded` webhook handler as `payments.refundedAmountCents` (cents);
on-time uses `payments.dueDate`, the guest's `rentDueDate` captured at charge time
in `handlePaymentIntentSucceeded` (an approximation — no per-charge schedule
history). `hoursSavedEstimate` (#32) credits `MINUTES_SAVED_PER_STRIPE_COLLECTION` (10) minutes per windowed payment with a `stripePaymentIntentId` (autopay or the resident's own Stripe payment; manual records have none), with `automatedCollectionCount`; it is labelled an estimate in `caveats`. The phone's Payment Dashboard shows it in `RentRoiCard` (the owner and money staff, i.e. managers, as `listHousePayments` admits; plan-gated). On-time compares the house-local payment day with `dueDate`.

Oxford Network has `availableForSale: false` (P-8) — `isTierAvailableForSale()`
blocks it in `createOperatorSubscription` checkout while keeping the tier defined.
Absent flag ⇒ sellable.

### Server-side entitlement gate (paywall)

`util/entitlement.ts` (`enforceHouseEntitlement`) is the only server-side paywall. `active`/`trialing` grant, `past_due` grants until `guestGraceEndsAt` (the first failed invoice's `finalized_at` + 7 days, `util/grace.ts`: kept across retries and late delivery, anchored only to an invoice that is still open, cleared once Stripe says the subscription is live and when it goes `canceled` or `unpaid`), and `canceled`/`unpaid`/unknown statuses deny. Phase A: an absent `subscriptionStatus` is still **granted** and logs `entitlement.absent_status`. The kill switch `paywall/config.enabled` fails closed. Gated: `castOxfordVote`, `setOxfordEnabled`, `createInvitation` and claim grants. Payments, claim revocations, `redeemInvitation`, the billing escape hatches and reads are deliberately ungated. Don't "fix" them. The full ladder, the reasons and the testing trap are in `.claude/rules/regroup-paywall.md`, which loads automatically when you work in `regroup/functions/src/`.

The house's initial `subscriptionStatus` comes from the operator's status: `createHouses` writes it in its transaction, and `setHouseSubscriptionStatusOnCreate` (`triggers/firestore/index.ts`, on every `houses/{houseId}` create) re-derives it from `users/{superAdminId || ownerId}.subscriptionMetadata.status`. An unrecognised or missing operator status is stamped `canceled` (deny) and logged as `house.created_without_subscription`.

### Callable contracts

- **`createOperatorSubscription`** (`callable/subscriptions.ts`): input `{ user: { id, email?, subscriptionMetadata }, paymentMethod, houseType, tier, billingInterval?: "month" | "year" }`; `user.id` must be the caller and `email` is required. Refused with `failed-precondition` while `TIER_BILLING_ENABLED` is off (no legacy fallback; the legacy two-item block after it is unreachable), while the sales switch is closed, or for a tier not for sale (Oxford Network). An unknown tier is `invalid-argument`; a tier whose price env var is unset is `internal`. Before Stripe, `claimCheckout` (`util/checkoutGuard.ts`) reads the STORED user record, never the client's `subscriptionMetadata`, and refuses with `failed-precondition` and `details.reason` (M9: a signed-in existing account can check out on the web, and the callable is public): `plan-exists` for any status other than `""`/`canceled`, or any stored `subscriptionId` that isn't canceled (a second subscription would bill twice); `plan-ended` for `canceled` with a stored `tier` still for sale (Reactivate restarts it; signup would be a second trial); `not-operator-account` for a resident (`isGuest`) or staff (`isAdmin` without `isSuperAdmin`) account, which the app routes by that role; `no-account` with no user doc; `checkout-in-progress` while another checkout holds the lock. Allowed: never subscribed; `canceled` with no `tier` or a tier no longer for sale (Reactivate can't restart those); `incomplete_expired` (never started, no trial used, Reactivate refuses it). The check takes a lock in the same transaction (`subscriptionMetadata.checkoutStartedAt`, 2 minutes), so concurrent checkouts for different plans (different Stripe idempotency keys) can't both pass. Under the lock, `findLiveSubscriptionForUser` (`api/stripe.ts`) looks in Stripe for a subscription with this `metadata.userId` that the record doesn't show (the customers with the payload email first, which is consistent, then a metadata search, which lags): one is refused as `unrecorded-subscription`, and a failed lookup is `unavailable`. The lock is released only for errors `initializeTierCustomer` marks as before any subscription could exist (`failedBeforeSubscription`: the customer or card check), and after a reversed checkout's cancel succeeds; an ambiguous error after the create keeps it until it expires. A successful write clears it. It creates a single-item tier subscription, writes `users/{uid}.subscriptionMetadata` (and `potentialSuperAdmin: true` on the doc, which the app routes an unfinished operator by) and seeds the `subscriptions` doc, emails admin@regroup-app.com (binds `SENDGRID_API_KEY`), and returns the user with `subscriptionMetadata` and `claimGranted` (the `potentialSuperAdmin` grant).
- **`reactivateOperatorSubscription`**: `active`/`trialing` returns the stored record unchanged; `cancelling` un-cancels in Stripe; `canceled` creates a **new** tier subscription (needs tier billing on, a stored `tier` still for sale and the sales switch open; a tier-less or retired-tier record is refused, and checkout is the way back). Before Stripe it takes checkout's lock in one transaction (`claimReactivation`, `util/checkoutGuard.ts`: a status no longer `canceled` is `plan-exists`, a held lock `checkout-in-progress`), then `findLiveSubscriptionForUser` refuses a live subscription the record doesn't show (`unrecorded-subscription`). The lock is released only for errors marked before any subscription could exist, and the new record clears it. It seeds the new subscription's `subscriptions` doc and house statuses with Stripe's returned status; `past_due`, `unpaid` and anything else throw `failed-precondition` (fix payment in the billing portal).
- **`updateSubscriptionGuests` / `updateSubscriptionHouses`**: no Stripe call. Tier subscriptions only (no `tier` → `failed-precondition`); they record occupancy in `subscriptionMetadata.houses` against the tier's `maxResidents` / `maxProperties` caps. Adding a house needs the caller's primary owner record; removing one is refused while its house doc still exists.
- **`createPaymentIntent`** (`callable/payments.ts`): the house must have a Connect account with `stripeStatus === "active"`; currency is USD only; `amount` (integer cents) must be positive and at most what is owed (`rentOwed` + `choreFees`, nothing owed refuses); `paymentMethodType` is `card` (default) or `us_bank_account` and picks the method-aware `computeApplicationFee` (`util/rentFee.ts`). The idempotency key is the client's or `${guestId}-${houseId}-${day}`. Returns `{ clientSecret }`, or `{ alreadyPaid: true }` when Stripe replays an already-succeeded intent.
- **`listPayments` / `listHousePayments`**: `stripe.charges.list` on the house's connected account (empty when it has none), amounts returned in **dollars** (`amount / 100`). `listPayments` is for the resident named by `guestId` or an admin of their house; `listHousePayments` is house admins only.
- **`getTierCatalog`** (`callable/getTierCatalog.ts`): **no auth**, by design (the public pricing page a logged-out visitor sees; it returns no user data and no price ids). Prices come from `stripe.prices.retrieve` on the configured price ids, not from the config's `amountCents`; a missing or unretrievable price degrades to `null` for that interval instead of failing the catalog. Per-instance cache: prices 5 minutes (checkout charges the price Stripe holds at call time), the sales switch 60 s. Returns `trialDays` and `salesOpen` too. E2E only: with `e2e/faults.tierCatalogUnavailable == true` it throws `unavailable` (the BILL-008 Maestro flow). `util/emulatorFaults.ts` honours that doc only when `FUNCTIONS_EMULATOR === 'true'` and `GCLOUD_PROJECT === 'demo-regroup-e2e'`; anywhere else it returns false without reading Firestore. Keep any new e2e fault behind `isEmulatorFaultOn`.
- **`getAppConfig`** (`callable/getAppConfig.ts`): **no auth**, by design (the version gate runs before sign-in; it returns no user data). Returns `{ minVersion: { ios: string | null, android: string | null } }` from `config/app`; a missing doc, a value that isn't `x.y[.z]`, or a failed read gives `null` (no minimum), never an error. Cached 60 s per instance (a failed read is not cached; the Functions emulator reads every call).
- **`deleteAccount`** (`callable/account.ts`, App Store 5.1.1(v)): no input, always the caller's own account. Requires a sign-in at most 300 s old (`auth_time`, else `failed-precondition`); the App Review demo account is refused (`permission-denied`); a subscription that can't be verified as the caller's (`BillingNotVerifiedError`) is `failed-precondition` and is not cancelled; any other failure is `internal`, with `details.partial: true` when earlier steps already removed data. Runs the resumable orchestrator in `accountDeletion/`.
- **`finishOperatorSetup`** (`callable/finishOperatorSetup.ts`): recovers only houses with a primary owner record for the caller (`house-roles/{houseId}_{uid}`, tier `owner`, `primary: true`); candidates are `users.housesOwned` then the subscription houses map, capped at 25 (`MAX_CANDIDATE_HOUSES`, logged as `truncated`); it re-grants missing house claims and writes the operator setup flags.

### Invitations, admission tickets and house tiers

- **Records** (`util/houseRoleStore.ts`, policy in `util/houseRoles.ts`): `house-roles/{houseId}_{uid}` `{ houseId, tier, grantedBy, grantedAt, via, invitationId?, primary? }`, server-only (the rules read them with `get()`). Tiers: owner > manager > peer leader > resident; each grants only below it, and ranks are strict for every grant and revoke: only the primary owner may grant owner (a co-owner may not). Oxford houses too, until the Oxford admission PR.
- **Tier sources:** the record plus the account's LIVE claims (`getUser`, never the caller's token). **The owner is the record with `primary: true`**: `createHouses` writes it in its transaction; the backfill writes it only when server-written evidence agrees with both `superAdminId` and `ownerId` (see Deploy order step 1), otherwise lists the house for the owner (`--primary houseId=uid`). A house with no primary record fails closed: guest and senior-peer invitations are refused (`house has no owner record`) and nobody may grant owner. `houses.ownerId` is never trusted for authority (`houseTierOf`, removals, `authGuard`, `finishOperatorSetup`, which only recovers houses with a primary record for the caller, `createInvitation`, the subscription add-house check, and resident capacity, which counts against the primary owner's subscription). A superAdmin claim is a co-owner; an admin-claim holder with no record is a peer leader.
- **Grants write the record** (never lowering it): admin invitation or `addAdminAuthorization` (owner or co-owner) -> manager; `addAdminAuthorization` with superAdmin (primary owner only) -> co-owner; senior-peer invitation, `promoteGuestsToAdmin`, `addGuestAuthorization` with `isAdmin` (manager or above) -> peer leader; guest invitation -> resident. **Record before claims** in `addAdminAuthorization`, `addGuestAuthorization` and `promoteGuestsToAdmin` write the record, then the claims, then the record again (`recordRoleGrant` never lowers, so the second write undoes a revoke that lowered the record in between; the second write happens only while the live claims still back the tier, so a revoke that also removed the claim is never undone). A failed claims write leaves a record with no matching claim. It grants no more than the claims: tier checks need the live claim, and the rules rank a caller as `tierAndRank` does (primary record 4; owner record with the superAdmin claim 3; owner or manager record with the admin claim 2; peer-leader record with the admin claim 1; otherwise the claim's rank). As a target it still ranks by the record (rules cannot read another account's claims), so no shadow doc can be made for it and equal staff cannot discharge it (a manager or the owner can) until a retry or the backfill's stale pass. `recordRoleRevoke` reads the live claims inside its transaction; a revoke between a grant's first record write and its claims write is undone by the second record write, so only a grant that fails after its claims write keeps a lowered record (until it is retried or the backfill re-run). A promoted account's ID token keeps its old claims until it refreshes (up to an hour; the app force-refreshes at sign-in and app start, not when someone else promotes it), so the rules rank it by the old token meanwhile. `redeemInvitation` still writes claims first (its retry needs the record and `grantCompletedAt` together); a stranded redeem is completed by the retry, and the backfill records any admin-claim holder still without a record. **Revokes re-derive the record** from the claims left (highest remaining claim; the primary owner record is never lowered).
- **Ranks** (primary owner > co-owner > manager > peer leader > resident): removals in the callables (`assertMayRevokeAll`), and in the rules any staff change to a guest record's status, `moveOutDate` or house (departure, re-activation or move) and staff deletes, checked against the record's account before and after the write; a staff create or link of a guest doc to an account needs a rank strictly above that account (no shadow record keeping a peer leader's claims); a rank-0 record any staff may change; nobody changes these on their own record.
- **Invitations:** no self-invite; no guest or senior-peer invitation to someone who already lives in the house (only an admin invitation may: that is how a resident manager is promoted). At redeem: the inviter's live tier must still allow the role, the inviter cannot redeem it, and a guest or senior-peer invitation is refused to someone who already lives there. Fresh redeem sets `grantPending`; `completeGrant` sets `grantCompletedAt` with the tier in one transaction; a same-account retry grants nothing unless stranded (`grantPending`, no completion, unexpired +24h), which re-checks capacity and records occupancy. A used admission ticket is never overwritten, so a resident who left (discharged or evicted) can never be re-admitted by invitation: their redeem is refused, and staff ranked above them re-add them (a staff-created guest doc plus `addGuestAuthorization`). Not changed: letting a new invitation replace a used ticket would reopen a self-create path, so it needs its own review.
- **`peekInvitation` is unauthenticated:** the token is the credential. For a usable (unexpired, unredeemed) invitation it returns `houseId`, `role`, `invitedEmail`, `initialPhase` and `expiresAt`, so anyone holding an invite link learns the invited email address (SignUpForm pre-fills it).
- **Invitation link format:** `createInvitation` emails `https://<WEB_BASE_URL>/invite?token=<encoded token>` (`buildInviteLink(token, webOrigin)`; `WEB_BASE_URL` is plain `process.env`, default `https://regroup-app.com`, validated: https (http only for localhost/127.0.0.1), origin only; an invalid value is logged and falls back to the default, and an unset value outside `phoenix-cleanhouse` logs one warning). The mobile app accepts that form only on its own web origin (`RATS_WEB_URL`, default `https://regroup-app.com`), so a staging deploy must set `WEB_BASE_URL` to the staging web origin that the staging build uses. `util/inviteEmails.ts` and `createConfirmationEmail` (`util/user.ts`) put the link in the email as given (HTML-escaped in the html body only): no `com.rats.dev://` rewrite, no `/redirect?url=` wrapper (the web page and the app's unwrapping of it were removed on 2026-11-27: no invitation outside pre-launch testing used it), and the link is not decoded. The old `regroup-app://?type=invitation&token=` links in already-sent emails still open the app (`parseAppLink`).
- **Admission tickets:** written with the redemption, expiring `min(redeem + 7d, invitation expiry + 24h)`; `settleTicket` (onGuestWrite, every create) binds one doc and flags other non-staff docs in `guest-flags`; with no ticket a doc without `createdBy` is legacy/staff. `entitlingDocs` decides which active docs keep the claims. It still counts a doc created by staff of equal or lower rank (not changed: shipped builds send no `createdBy` and per-doc rank reads could strip a real resident; the rules now refuse new shadow records, and any made before step 3 need a one-off audit).
- **Departures** (onGuestWrite): a delete, an update from active to departed, or a move (`houseId` change; the old house's EES week is re-split, the new house's claims never granted) revokes the old house's guest claim, plus admin unless an owner/manager record or a live superAdmin claim remains; the record is re-derived. Current state decides, so redeliveries are no-ops.
- **Rules read limit on guest batches:** each departure, delete or account-linked create of a guest doc reads that account's `house-roles` record (one `get()`, which returns null for a missing record), plus the caller's record once per batch; a move between houses reads both houses. A batch may make 20 reads, so one batch carries at most 19 account-linked removals or discharges, or 9 moves between two houses (measured in the emulator). The app removes and discharges one guest doc at a time, so the limit does not affect it (`services/house.tsx` `updateHouseBatch`, which chunks through `services/guestBatch.ts`, has no caller).
- **Stale tokens:** after a demotion the ID token keeps the removed claim for up to an hour, so rules (which read the token) still accept it in that window; callables read live claims. Forced sign-out (`revokeRefreshTokens`) is not used: it would sign multi-house staff out everywhere.
- **Not moved to records (report):** payments authority (`util/houseAuth.ts`, `callable/payments.ts`) still reads `ownerId`, `adminId`, `adminIds`, `superAdminIds`. Until step 3 (rules live) a superAdmin of the house can write all four; after step 3 `ownerId` is server-only, while `adminId`, `adminIds` and `superAdminIds` stay writable by a superAdmin of the house (owner decision pending); the `superAdminId`-missing fallback in `triggers/firestore/index.ts` and the account-deletion queries are unchanged.

### Webhook security

`webhooks/stripeWebhook.ts` uses Stripe signature verification (`stripe.webhooks.constructEvent`). Never process a webhook payload without verifying the signature first.

Subscription events (`customer.subscription.created`/`updated`) re-read the subscription from Stripe and write that state, not the payload's, to the `subscriptions` doc, the operator's houses and `users/{uid}.subscriptionMetadata.status` (`webhooks/subscriptionState.ts`), so a late or out-of-order event can't move it backwards. `cancelling` there means set to cancel at period end. A subscription with no `subscriptions` doc is skipped before any Stripe call.

Subscription events `stripeEvents` handles: `customer.subscription.created`/`updated`/`deleted`/`trial_will_end`, `invoice.payment_succeeded`/`payment_failed`/`payment_action_required`. The live endpoint's event list must include every one. `trial_will_end` and `payment_action_required` only push to the operator (`webhooks/subscriptionNotices.ts`). A subscription whose metadata has `regroup_launch_cancel: "true"` is canceled everywhere with no push: the launch cancellations are explained by the owner's notice.

### Firestore gotchas

**House owner fields.** `createHouses` stores the operator's uid in `ownerId` and `superAdminId`; `adminIds`/`superAdminIds` hold admin-record ids from `createAdminId()`, not uids. Find an operator's houses by `ownerId`: `adminIds array-contains uid` matches only legacy houses (#222). For the same reason, never address a notification to an `adminIds` entry: `notifyOperatorOnApplication` resolves staff uids from the role records (`staffUids` in `util/houseRoleStore.ts`) plus `superAdminId`.

**admins records copy the user's name and phone.** `onUserAdminProfileSync` (`triggers/firestore/adminProfileSync.ts`, retried, `util/eventAge` cutoff) copies `firstName`, `lastName` and `phoneNumber` from `users/{uid}` onto every `admins` record with that `userId` (ids are `createAdminId()` auto-ids, so find them by `userId`; a user may have none or several) whenever one of the three changes. Each record is a transaction that re-reads the CURRENT user doc (`admins/profileSync.ts`), so out-of-order and redelivered events converge; a field the user doc doesn't hold as a string is left alone. The app's `EditUserInfoForm` still copies its fields (avatar, date of birth, phone and others) to the admins record, but only once that record has loaded; for name and phone the trigger is the backstop. The other fields have no server copy. Only `users` updates trigger it: an admins record created later takes its name from its creator (`createHouses` copies the user's), and its phone only from the next change.

**Deleted houses leave a tombstone.** `onHouseDeleted` (`triggers/firestore/houseTombstone.ts`, retried) writes server-only `houseTombstones/{houseId}` (`deletedAt`), which `createHouses` (`houses/createHousesTx.ts`) reads to refuse a tombstoned id, and frees the house's slot in the owner's `subscriptionMetadata.houses` in a transaction (the property-cap count). Both happen some time after the delete, not with it.

**week-summaries are server-owned.** `onActivityWritten` recomputes the touched guest-week(s) from `activities` in a transaction on every activity write (house-local Monday week via the guest's `houses.timezone`, default `America/New_York`; every activity counts unless `status == "deleted"` or `incomplete == true` (an admin-approved dispute, recorded with `disputeOutcome: 'incomplete-per-residents'`; disputed activities are never deleted, see regroup/CLAUDE.md) — pending and rejected disputes count; the court compliance export lists meetings by the same rule (its Dispute History column reads the decision log, the trusted record). On a transition into `disputed` it notifies the house admins (`adminIds`/`superAdminIds`/`superAdminId`) and the resident minus the disputer, who is the `disputedBy` (older builds: `disputeResolvedBy`) that the entering write set; the rules require it to be `request.auth.uid` for every caller. Firestore's auth-context `authId` is not documented as the Auth uid, so it is not used (`activities/disputeNotifications.ts`, idempotent per event). A REOPEN (an admin undoing a decision: `resolved`, or an older build's "delete", back to `disputed`) notifies the same people minus the reopener: "A dispute decision was undone; the dispute is open again." It maintains the live dispute list `house-disputes/{houseId}` (server-only, the app reads it; `house.disputes` is still written as an untrusted, display-only legacy mirror for older builds), the server-only `dispute-archive` (the trusted record with the decision log; `/disputes` is the legacy, client-writable, untrusted collection older builds write) and the decision log in one transaction (`activities/houseDisputeMirror.ts`, `activities/disputeDecisions.ts`): (1) a write that leaves `disputed` logs `activities/{id}/dispute-decisions/decided_{disputeResolvedAt ms}` (approved | rejected | kept | deleted, with `by` and `at`), and a reopen logs `reopened_{reopenedAt ms}` with the outcome it undid, both from the event payload and never rewritten (a redelivery that disagrees with an existing entry logs `dispute_decisions.conflict`; the ids must be time-based because the rules derive `decided_…` from `disputeResolvedAt`, and each activity's subcollection holds only a handful of decisions, far below the write rates where sequential keys hot-spot); the rules allow a reopen only once `decided_…` exists, so no decision is undone before it is logged; (2) the dispute that event decided is archived to `dispute-archive/{activityId}_{decision id}`, built from the decision and the activity payload only and written with `create()` (a disagreeing redelivery logs `dispute_archive.conflict`) with that decision's outcome and resolver, even when the close is processed after a reopen or a later dispute, so re-deciding a reopened dispute never overwrites an earlier archive; (3) the live list is reconciled from the activity's current state: while `disputed`, the server's own entry is kept if it has this dispute's `disputeStamp` = hash(disputer, reason, `disputedAt`), else a new one is built from the activity; otherwise every entry for the activity is removed. Nothing is ever copied from the legacy `house.disputes` map (admins can write it); its keys for the activity are only deleted, and it gets the live entry as a mirror. A reopened older-build dispute (disputer only in `disputeResolvedBy`) gets `disputedBy` back from that dispute's decision log entry, onto the activity too; decisions backfilled for pre-deploy disputes carry no disputer (older builds had overwritten it), so those get none back. An activity id that cannot be a map key (the rules now refuse those at create) is left out of the lists and logged; its decisions are still logged and archived. It also fills `residentUid` (the resident's account, from `guests.userId`) when it is absent or null (`activities/residentStamp.ts`); no client changes it after create (new app builds set it at create, checked by the rules); the server re-stamps it only on an admin's `guestId` correction before any dispute (see below), and `onGuestLinkedRestamp` (`activities/guestRestamp.ts`, separate from `onGuestWrite`, with `util/eventAge`'s `RETRY_CUTOFF_MS` cutoff) only fills empty stamps on a guest's activities when its `userId` is linked or changed, skipping stamped ones without a transaction. An activity that cannot be stamped gets `residentUid: null, residentUidPending: false` once (logged once), so later writes skip the transaction (a fill that fails is left pending instead, so the next write or the backfill fills it). An admin correcting `guestId` before any dispute re-stamps it from the new guest; once there is dispute history the rules freeze `guestId`, so a disputed activity's stamp never moves. With no usable stamp the rules fall back to the guest doc (any admin but the logger when it has no account or is missing), which relies on #145's guest rules. Clients can never change it. A decision or reopen by the activity's resident (guest `userId` or stamp) or logger is logged as `dispute.self_decision` (ids only) and flagged in the server-only `flaggedForReview` (`activities/selfDecisionCheck.ts`). Residents may no longer write `house.disputes`. Besides the mirror, one server consumer of that untrusted map remains: the scheduled `updateDisputes` job (`scheduled/disputeUpdates.ts`, old dispute model), which writes legacy guest week fields, `house.disputes` and `/disputes`; none of them feed the week summaries, the export or any money path. Activities are client-written, so nothing in them is trusted: the summary's `houseId` comes from `guests/{guestId}`, and an activity counts only if its `houseId` is the guest's house and `loggedBy` is the resident (`guests.userId`) or an admin/superAdmin of that house per Auth custom claims (`activities/activityTrust.ts`). Writes are absolute values, so redelivery is a no-op. Don't add client-side summary writes back. **Rollout:** app builds released before the trigger still write summaries — +1 on log, -1 on delete, and a full client recompute on edit/resolve (window Monday 00:00 UTC through `weekEnd + 'T23:59:59'` device-local, counting every activity with the guestId). Any of these can land after the trigger and overwrite its value, and nothing re-triggers until the next activity write for that guest-week. Old resident builds also keep producing duplicate activities (error after save → retry). Re-running `backfill:week-summaries` once those builds are retired is MANDATORY (dry run first; it reports suspected duplicates and closed-week rewrites).

Known limits of the week-summary recompute (by design, not bugs to "fix" silently):

- **Only activity writes trigger it.** Nothing recomputes when a guest doc changes (e.g. `userId` set after the resident's activities were logged by an admin import, or a house move), so that guest's summaries stay stale until the next activity write in each affected week. Run `backfill:week-summaries` (optionally `--house`) after such a change.
- **House moves exclude history.** An activity counts only if its `houseId` is the guest's _current_ house, so a guest moved between houses has their earlier activities excluded as `otherHouse` on any recompute of those weeks. No transfer UI exists today; if one is added, decide whether summaries follow the guest.
- **Dates are the resident's to choose on create.** The rules let a resident log a backdated or future-dated activity (the forms allow picking a date); only _updates_ are limited to dispute, delete and an admin's decisions (a reopen restores only the count an approval removed).
- Admin claims are resolved before the transaction (no Auth calls while it holds locks), and the transaction re-reads the guest and its house: if the house or its zone changed since the week was computed it throws `week_summary.guest_changed` (code `aborted`) and the event retries. The backfill aborts on it; re-run it.

**Indexes are NOT deployed by `deploy:rules`.** `regroup/mobile/firebase/firestore.indexes.json` is the source of truth (wired via `mobile/firebase/firebase.json`); `mobile`'s `deploy:rules` is only `--only firestore:rules,storage`. Deploy indexes with `cd ../mobile && npm run deploy:indexes`. A `balance`→`rentOwed` rename in `6e67faf` (2026-06-01) left the committed index stale, and `scheduledRentCollection` threw `FAILED_PRECONDITION` on every single run for months while Cloud Scheduler went unwatched. After changing any composite query, run `deploy:indexes` and confirm the index reports READY.

Never key a document on a timestamp or counter — Firestore shards by key range, so sequential keys concentrate writes on one range instead of spreading them. Use `collection.doc()` auto-ids and keep the time in a `createdAt` field.

### Live reads (phoenix-cleanhouse)

The firebase MCP server can't query regroup. Read Firestore with ADC and the REST `runQuery` endpoint, and read Gen2 logs with `resource.type="cloud_run_revision"` and a **lowercased** `service_name` (about 30 days of retention). The commands are in `regroup/functions/docs/live-reads.md`.

### Test mocking

Shape a mocked doc the way its production writer writes it, and make query mocks match on field values. The webhook test once mocked houses with `adminIds: [uid]`, which hid #222, and the Oxford tests mocked a price for a tier that doesn't exist, which hid #225.

A `jest.mock(path, () => importedConstant)` factory that returns a value **imported** from a test helper throws `ReferenceError: Cannot access '<helper>_1' before initialization` — jest hoists the factory above the import, and it runs during the hoisted import of the module under test. Inline shared mock _values_ in each factory; only shared _behaviour_ survives extraction, because an arrow like `doc: (id) => store.doc(id)` reads the outer binding lazily at call time.
